# 设计功能测试用例

## 1. 确定测试依据

1. 确定模块、版本和测试范围。读取用户指定的当前 PRD 或用户故事及验收标准，按项目规则核对已确认的变更、不做范围和待确认问题。只读取与范围相关的原型、字段字典、权限矩阵、状态流转表和接口约定。
2. 按验收标准列出可测试条件。记录模块、现有编号和来源章节。没有编号时，用文件与章节定位。原型用于识别页面和操作，台账用于核对字段、权限与状态。当前确认的规则与原型现状不一致时，按确认规则设计预期，另列原型差异。正式依据之间冲突且无法按项目口径判定，或规则本身缺失时，把受影响的部分列为待确认，并继续设计其余场景。
3. 更新已有用例时，先按模块、页面／功能和测试编号定位条目，沿用项目编号规则。引用验收编号时带上所属模块，跨文档时注明 PRD 文件或版本。同一行为只保留一条等效用例，合并时保留全部适用的需求引用。执行条件或预期不同的角色保留独立用例。

## 2. 推导覆盖

从正常流程开始，按规则和失败影响选用适用的方法。优先级沿用项目约定。没有约定时，按业务影响和风险给出建议的高／中／低优先级，并写明关键风险。

| 规则特征 | 设计方法 |
| --- | --- |
| 输入格式、枚举、必填或取值范围 | 等价类划分。按规则选择有代表性的有效和无效数据。已知有序边界时，用边界值验证阈值两侧与边界本身。 |
| 多个条件共同决定结果 | 判定表。列出可行组合，例如角色 × 数据归属 × 状态。先隔离验证每个独立拒绝条件，再覆盖有不同结果、规则优先级或额外风险的交叉组合。抽样时说明省略范围。 |
| 审批、退回、取消、重提等流程 | 状态迁移。记录起始状态、角色、触发动作和目标状态。对已规定的拒绝路径验证状态和数据是否保持原样。 |
| 查询、空态、失败和恢复 | 分开验证有结果、无记录、无匹配和请求失败等有不同表现的场景。按已确认规则补重试、重复提交或数据一致性。 |
| 页面、按钮、字段及数据权限 | 分别考虑允许访问与拒绝访问。页面或按钮表现通过 UI 检查；服务端拒绝与未写入需要用相应环境的接口、持久化读回或审计证据验证。 |

按范围保留有不同执行条件或判定的用例。未确认的最大长度、错误码、正式提示语和权限边界进入覆盖缺口，记录影响的验收条目和所缺依据。可以把有价值的额外场景标成「建议补充」，等待确认后纳入验收。

## 3. 写成可执行用例

- 每条用例有一个主要判定目标。前置条件写清账号权限、数据归属、初始状态和所需环境。优先用可重建的合成数据，给出可区分的输入值或数据准备方法。
- 用编号步骤写可执行动作。关键步骤的预期结果写清检查对象、观察位置和可判定的结果。需要验证副作用时，按依据说明哪些记录应该出现、改变或保持原样。有必要时写出数据清理或恢复方式，避免依赖其他用例的执行顺序。
- 区分原型走查和联调验收。原型走查限于原型实际具备的可见状态和交互。涉及服务端鉴权、落库、并发或审计的用例标明需要的接口、账号、数据控制或证据能力。环境暂不可用时保留已设计的用例，单独标注执行依赖。
- 新设计的用例标为「未执行」。实测另按用户指定的范围进行，以环境、版本和证据记录结果。更新已有用例时保留已有执行记录，并指出受规则变更影响、需要复测的条目。

## 4. 交付并核对

默认在对话输出 Markdown。用户指定项目文件时，沿用现有格式和字段。若写入项目的 `07_测试验收/功能测试点.csv`，沿用表头，在「前置条件」写测试数据及环境，在「备注」保存关联验收编号和依据。针对请求范围合并，保留其他条目。

1. **用例表**　测试编号｜关联模块与验收编号｜场景｜优先级｜前置条件与数据｜步骤｜预期结果｜执行状态。
2. **覆盖与缺口**　逐条核对范围内的验收标准，列出关联用例编号和设计覆盖状态（已设计、部分覆盖、未覆盖、待确认或不适用），说明缺口原因。执行状态和环境依赖另记。范围小时用简表，范围大时按模块汇总并保留逐条映射。
3. **交付检查**　确认编号能回溯到依据，步骤和预期能逐一对应，预期可由另一个人判定，权限检查的证据层级与结论匹配。报告仍需确认的规则、资料冲突或执行前置条件。
