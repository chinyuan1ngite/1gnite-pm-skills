# 某政务项目 AI 工作规则

## 1. 项目定位

本项目为某政务项目服务平台产品设计资料库，用于维护：

- PRD
- HTML 原型
- 页面清单
- 字段字典
- 权限矩阵
- 状态流转
- 反向补档
- 差异检查

## 2. 输出原则

- 不得编造未确认业务规则。
- 正式 PRD 必须区分【事实】【推断】【建议】【待确认】；反向补档 PRD 按第 6 章的例外规则执行。
- 已确认删除的功能，不得重新加入。
- 旧系统功能必须标记为：
  - 继续办理
  - 停用但保留查询
  - 完全废弃
  - 待确认
- 任何 PRD 输出必须包含“不做范围”和“待确认问题”。

## 3. 项目固定口径

- 专家评审端仅保留：登录/校验、评审任务查看、申报材料查看。
- 消息通知入口放在顶部导航栏右上角。
- 单位经办端“本单位申报审核”去掉“批量报送”按钮。
- 单位信息默认不可编辑，修改信息需提交审批。
- 个人申报总工作台不展示资料完整度。
- 事项配置需考虑表单、流程、规则、权限、版本快照。
- 开发页面反向补档时，不得直接把页面现状视为最终需求。

## 4. 文档格式

PRD 使用 Markdown。
原型使用 HTML + CSS。
流程图使用 Mermaid。
台账使用 CSV。
正式交付可后续转 Word / Excel。

## 5. HTML 原型规则

- 不使用 emoji。
- 后台页面保持政务管理端风格。
- 使用 common.css。
- 不要重复写大段内联样式。
- 页面必须包含：标题、说明、筛选区、主内容区、操作区、状态区。
- 弹窗、抽屉、空态、异常态需要单独说明。

## HTML 原型视觉与组件约束

### 1. 极简主义与信息密度

HTML 原型必须严格遵循重型 B 端系统的设计哲学。

设计目标不是视觉装饰，而是：

* 信息清晰
* 操作高效
* 状态明确
* 密度合理
* 便于开发落地
* 便于测试验收

必须避免：

* 无意义视觉装饰
* 杂乱图标
* 大面积无效留白
* 过度卡片化
* 过度圆角
* 过度阴影
* 过度渐变
* 大屏化装饰风
* 营销化视觉风格
* 与业务无关的插画和图案

后台页面应优先保证表格、筛选、状态、操作和详情内容的可读性。

---

### 2. 组件化思维

页面构成必须基于标准且成熟的 B 端组件库形态。

可使用的组件形态包括：

* 顶部导航
* 左侧菜单
* 面包屑
* 页标题
* 查询表单
* 数据表格
* 分页
* 标签页
* 卡片
* 描述列表
* 表单
* 步骤条
* 状态标签
* 操作按钮
* 弹窗
* 抽屉
* 提示条
* 空状态
* 加载状态
* 错误状态

禁止使用无法稳定落地的自定义异形交互，包括但不限于：

* 非标准悬浮异形面板
* 过度动画式菜单
* 不规则图形按钮
* 大量装饰性图标
* 复杂拖拽交互
* 非必要瀑布流
* 非必要大屏组件
* 需要高成本定制开发的交互组件

所有 HTML 原型应尽量贴近 Ant Design、Element Plus、Arco Design 等成熟 B 端组件库的通用形态。

---

### 3. 页面层级与交互方式

页面模块不得为了展示完整而在同一页面中堆叠平铺。应根据任务关系、信息复杂度和用户操作习惯，合理划分页面层级与交互方式。

必须遵循：

* 独立业务任务、复杂详情、长表单或需要独立导航定位的内容，应设计为二级页面。
* 新增、编辑、确认、删除等短流程操作，适合在当前上下文完成的，应使用弹窗。
* 辅助查看、快速选择、关联配置等需要保留当前页面上下文的内容，可使用抽屉。
* 同一页面只承载当前任务必需的信息与操作，不得把列表、详情、表单和全部配置模块无差别平铺。
* 页面跳转、返回路径、弹窗关闭、抽屉收起及操作后的状态反馈必须完整可用。
* 交互方式必须符合用户直觉和常见 B 端系统使用习惯，不得为了减少页面数量而牺牲可读性与操作效率。

生成原型前，应先判断每个模块属于当前页内容、二级页面、弹窗还是抽屉，再进行页面实现。

---

### 4. 状态完备性

页面设计必须穷举数据生命周期与异常状态。

每个列表页至少考虑：

* 初始状态
* 加载中
* 有数据
* 无数据
* 查询无结果
* 接口异常
* 权限不足
* 批量选择状态
* 分页状态
* 筛选条件已生效状态

每个详情页至少考虑：

* 加载中
* 正常展示
* 只读状态
* 编辑状态
* 审批中
* 已退回
* 已办结
* 数据不存在
* 权限不足
* 附件加载失败
* 操作成功
* 操作失败

每个表单页至少考虑：

* 新增
* 编辑
* 只读
* 草稿
* 校验失败
* 保存中
* 保存成功
* 提交确认
* 提交中
* 提交成功
* 提交失败
* 退回补正
* 已过期 / 不可办理

所有状态必须有明确的页面表达，不得只写在 PRD 中而不在原型中体现。

## 6. 反向补档规则

从开发页面反向生成文档时，输出：

1. 页面现状
2. 字段清单
3. 按钮清单
4. 表格列
5. 弹窗/抽屉
6. 状态/枚举
7. 权限推断
8. 与原需求差异
9. 待确认问题
10. 修正建议

反向补档 PRD 采用以下专用写法：

- 正文不使用【事实】【推断】【建议】【待确认】【历史资料】标签，也不写标签体系、事实分级或分类方法的说明。
- 对外交付的 PRD 只保留业务需求内容，不描述反向整理、页面采集、文档生成或原型制作过程，不出现 Agent、AI、工具名称、内部规则文件、目录路径、环境网址、账号或密码。
- PRD 的来源说明不得出现系统访问网址；环境地址、采集日期、采集账号及原型文件路径仅保留在内部任务记录或采集台账中。
- 通过“页面现状、设计补充、差异说明、待确认问题、来源与依据”等章节或表格列区分内容性质。
- 无法确认的内容只集中登记在“待确认问题”表中，使用“待确认-xxx”稳定编号；正文需要引用时直接写“见待确认-xxx”，不增加方括号标签。
- 开发页面、截图、源码及历史材料的来源性质保留在内部采集或差异记录中；PRD 仅写对理解业务规则有必要且可对外展示的依据。
- 本例外仅适用于反向补档 PRD；内容仍须可追溯，不得把页面现状、推断或设计补充写成已确认业务规则。反补内容转为正式 PRD 后，恢复执行第 7 章的通用标签规则。

## 7. PRD 生成规则

### 7.1 口径优先级

- 某政务项目固定口径、已确认修改意见和不做范围，优先级高于历史 PRD 的任何写法或内容。
- 历史 PRD 仅可用于参考文档结构和表达方式，不得迁移其中的角色、流程、字段、状态、权限、提示语或业务规则。
- 需求来源优先级依次为：项目固定口径、已确认意见、已确认会议纪要、正式文件及接口材料、当前有效 PRD 与原型、历史资料、产品推断与建议。
- 除第 6 章规定的反向补档 PRD 外，所有内容必须区分【事实】【推断】【建议】【待确认】【历史资料】。
- 无法追溯来源的精确数值、时限、比例、枚举、审批节点、接口字段和提示文案，不得写成事实。

### 7.2 PRD 结构要求

- PRD 必须使用 Markdown，并遵循 `00_项目口径库/PRD结构模板.md`。
- 后续 PRD 默认采用“平台通用能力型”组织风格：先说明业务背景与产品定义，再列能力架构和功能清单，随后展开核心功能、字段、状态、权限、异常、数据和验收要求。
- 第二版风格负责文档组织和表达效果；原有结构规范继续作为完整性和质量底线，两者合并执行，不再作为两套可选规则。
- 必须包含：文档说明、修订记录、业务背景与产品定义、适用范围、不做范围、用户角色、页面清单、业务流程、能力架构与功能清单、核心功能说明、字段说明、状态流转、权限控制、校验规则、异常场景、接口/数据/非功能要求、日志留痕、消息通知、验收标准、待确认问题。
- 条件章节不适用时，应保留章节并说明“不适用”原因。
- 标题层级原则上不超过三级。
- 每份 PRD 应对应一个业务模块或一组强相关页面；跨越多个独立业务闭环时应拆分文档。
- 正文中的页面、功能、字段、规则、状态、权限、异常和验收标准应使用稳定编号并建立引用关系。
- 页面级 PRD 可裁剪不适用的技术架构、部署和运维内容，但不得删除接口、数据、非功能和测试验收所需的说明。

### 7.3 功能点描述要求

每个功能点必须包含：

1. 功能名称；
2. 功能说明；
3. 前置条件；
4. 输入；
5. 处理规则；
6. 输出；
7. 异常场景；
8. 权限控制；
9. 验收标准。

其他要求：

- 核心功能展开前必须先提供能力架构与功能清单，功能清单与功能明细一一对应。
- 每个功能点增加“需求来源”，并引用真实存在的来源编号。
- 功能名称使用“对象 + 动作”命名。
- 一个功能点只描述一次可操作、可反馈、可验收的功能单元。
- 用户动作与系统响应必须分开描述。
- 处理规则应注明触发条件、执行顺序、状态变化及关联接口。
- 输出应说明页面反馈、数据变化、状态变化、待办、消息或跳转。
- 按钮必须说明出现条件、可用条件、前置校验、成功结果和失败处理。

### 7.4 字段表要求

- 查询字段、表单字段和列表字段必须结构化列出，一个字段一行。
- 表单字段至少说明：字段名称、控件类型、必填性、默认值或回显、数据来源、可见及可编辑条件、校验规则、联动规则、脱敏要求和错误提示。
- 列表字段至少说明：数据来源、展示格式、排序或筛选、权限与脱敏、空值处理。
- 条件必填必须写明触发条件和取消条件。
- 下拉项、状态和类别必须引用已确认字典；无字典来源时标记【待确认】。
- 原型示例值不得直接作为正式字段枚举或验收预期。
- 完整技术字段定义统一维护在字段字典中，PRD 通过字段编号引用。

### 7.5 流程与状态要求

- 流程必须说明参与角色、触发条件、前置条件、主流程、分支流程、异常流程、结束条件、后置结果和状态变化。
- 主流程应分别列出操作角色、用户动作、系统响应、状态变化和关联页面。
- 分支流程必须注明来源步骤、触发条件及回归点或结束结果。
- 跨角色流转必须说明上一角色的输出、下一角色的待办来源和数据范围。
- Mermaid 流程图仅用于辅助理解，不能替代流程步骤表。
- 文档状态、业务状态和页面状态必须分开定义。
- 业务状态必须集中维护；每个非终态都应具有合法退出路径。
- 状态必须与按钮、权限、流程和页面表现保持一致。
- 列表页、详情页和表单页必须覆盖 `AGENTS.md` 规定的适用状态及异常状态。

### 7.6 权限控制要求

- 权限必须同时覆盖：
  - 菜单及页面权限；
  - 按钮及操作权限；
  - 数据范围权限；
  - 字段可见及可编辑权限。
- 角色名称必须引用项目角色权限口径，不得自行创造同义角色。
- 数据范围必须使用本人、本单位、授权组织等可判断边界，不得使用“相关数据”等模糊表达。
- 无权限表现必须明确为隐藏、置灰、只读或提示。
- 前端隐藏不能替代服务端鉴权。
- 权限规则必须与页面、状态流转、按钮操作表和权限矩阵一致。

### 7.7 验收标准要求

- 每个关键功能、规则、校验、异常和权限场景必须关联验收标准。
- 验收标准采用“前置条件—操作—预期结果”结构：
  - 前置条件：角色、权限、业务状态和数据条件；
  - 操作：用户执行的明确动作；
  - 预期结果：可观察的页面反馈、数据变化和状态变化。
- 一条验收标准只验证一个主要结果。
- 验收范围应覆盖正常、边界、异常和无权限场景。
- 禁止使用“功能正常”“展示正确”“操作友好”等不可判断表达。
- 验收标准必须能够直接转化为测试点。

### 7.8 禁止事项

- 禁止从历史 PRD 中迁移任何具体业务规则。
- 禁止因历史 PRD 存在某个角色、字段、状态或流程，就将其加入某政务项目。
- 禁止将旧系统页面现状直接视为最终需求。
- 禁止编造未确认的角色、流程、枚举、状态、字段、权限、接口、时限、比例或提示文案。
- 禁止伪造会议纪要、政策文件、确认人、来源编号或确认状态。
- 禁止恢复已确认删除或已列入不做范围的功能。
- 禁止仅使用截图或原型表达需求，必须提供可检索的文字规则。
- 禁止将多个字段、规则、状态和异常压缩在一个长段落中。
- 禁止混用事实、推断和建议。
- 禁止保留未处理的模板占位符或无说明的空章节。
- 禁止 PRD 与原型、字段字典、权限矩阵、状态流转表和测试点长期不一致。

### 7.9 中文编号规则

- 面向业务阅读的标题使用中文序号，例如“功能一：查询评委会”“页面一：评委会管理”。
- 跨章节引用使用“中文名称 + 三位数字”的稳定编号，例如“功能-001”“页面-001”“字段-001”“验收-001”。
- 每份 PRD 独立编号；页面、功能、字段、规则、状态、权限、校验、异常、接口、数据、日志、验收、待确认、不做范围等各类别均从 `001` 开始并在文档内连续递增。
- 编号只要求在同一份 PRD、同一类别内唯一；跨文档引用或结构化台账检索使用“模块/PRD 名称 + 稳定编号”作为联合标识，不得仅凭编号判断所属模块。
- 统一使用以下中文编号前缀：来源、页面、功能、输入、输出、规则、字段、列表字段、操作、业务状态、页面状态、权限、校验、异常、接口、数据、字典、日志、消息、验收、待确认、不做。
- 新生成或升级为当前有效版本的 PRD 不得继续使用 `FUNC`、`PAGE`、`FIELD`、`ACTION`、`STATE`、`PERM`、`VAL`、`EX`、`AC`、`Q` 等英文编号前缀。
- 历史归档文档可保留旧编号，避免破坏历史引用；历史内容升级为当前版本时必须转换为中文编号。
- 中文序号只用于标题展示，正文引用必须使用稳定编号，不得仅用“功能一”“规则一”作为跨章节引用。

## 8. 本地环境与工具规则

- 执行 Word、Excel、PDF、Mermaid 或 HTML 渲染任务前，先检查当前环境、项目脚本和依赖是否满足任务要求。
- 使用 Codex Desktop 时，优先加载 Codex 提供的工作区隔离运行时和文档处理库，不在项目中硬编码用户缓存目录。
- 需要本地 Python 脚本时，以 Python 3.12 作为项目兼容基线，并使用项目虚拟环境；不得把 `.venv`、`node_modules` 或转换缓存作为项目资产提交。
- Word 和旧版 `.doc` 转换必须具备 LibreOffice；正式生成或修改文档后执行结构、样式、编号、表格、占位符和文件可打开性检查，不强制进行逐页渲染或视觉验收。
- 生成 PRD Word 交付版时，以 Markdown PRD 为内容主版本，使用团队提供的干净模板（如有）、`Word排版规范.md` 和 `Markdown与Word样式映射表.md`；脱敏示例仓库不附带原项目二进制模板。
- Word 模板只控制页面、字体、标题、编号、表格和封面等排版，不得从模板来源文档迁移具体业务内容、作者、日期、模块或编制单位。
- Word 标题必须使用真实样式和自动多级编号；`功能-001`、`字段-001`、`验收-001` 等中文稳定编号保持正文原样，不参与章节自动编号。
- DOCX 交付前必须检查文件可打开、内容完整、样式映射、自动编号、表格结构、中文稳定编号和占位符；仅在用户明确要求视觉验收时按需渲染或抽查页面。
- HTML 原型必须在 Chromium 内核浏览器中检查中文、样式、交互和适用状态。
- 项目文本及 CSV 统一使用 UTF-8；出现乱码时先检查读取方式和编码，不直接覆盖原文件。
- GitLab 凭据必须交给系统凭据管理器，不得写入远端 URL、Markdown、脚本、日志或提交记录。
- 环境缺失或版本不兼容时，先说明受影响任务和验证结果；未经用户授权，不擅自安装系统软件或修改系统级环境变量。

## 9. 视觉设计生图规则

- 配套视觉生图 Skill 位于 [`../../skills/government-project-visual-design`](../../skills/government-project-visual-design)，仅在用户显式调用 `$government-project-visual-design` 时使用。
- 视觉生图用于生成独立的高保真页面概念图和汇报图片，不属于 HTML 原型生成流程，不继承 `04_HTML原型/common.css`。
- 视觉生图必须直接使用图片生成能力，不使用浏览器截图、HTML 截图或原型截图替代。
- 默认只使用用户本次提供的主题、文字、数据和参考图片，不主动读取 PRD、原型、台账、原始资料和测试材料。
- 用户提供参考图时，先提取配色、布局、信息层级、组件形态、材质和信息密度，再以用户的新主题生成全新构图；不得复制参考图的具体页面和业务内容。
- 视觉生图不使用或生成 Logo；参考图中的 Logo、品牌名称、水印、人物、业务文字和数据不得进入新画面。
- 汇报图片未附参考图时，从 Skill 内置参考集中按内容结构选择一张主参考图，必要时最多增加一张辅助参考图；不得默认同时使用全部参考图。
- 内置汇报图参考集不自动用于高保真页面概念图，除非用户明确要求。
- 数据大屏高保真图仅作为独立视觉概念稿生成，不属于 HTML 原型；仅在用户明确指定“数据大屏、驾驶舱、运行态势或监测看板”时进入大屏路由。
- 数据大屏默认读取 `references/data-dashboard-guidelines.md`，不得自动套用内置汇报图参考集。
- 数据大屏未提供精确数据时，不得生成看似真实的随机数字、比例、排名、日期、地图边界和区域热点。
- 默认只在当前对话返回图片，不向项目目录写入生成物，不修改项目配置、业务资产、依赖或 Git 状态。
- 用户明确指定项目文件作为内容来源时，仍须区分事实、推断、建议和待确认，不得补造业务规则或精确数据。
- 视觉生图结果属于视觉示意，不替代 PRD、HTML 原型、结构化台账和测试验收依据。
