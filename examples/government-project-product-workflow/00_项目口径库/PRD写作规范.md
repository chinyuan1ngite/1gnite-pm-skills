# 某政务项目 PRD 写作规范

## 1. 适用范围

本规范用于某政务项目的模块级、页面级和流程级 PRD 编写、评审与维护。

本规范已吸收“第二份：通用模块产品 PRD 样例”的平台通用能力型组织方式。后续 PRD 默认使用该风格，不再将第一版和第二版作为两套可选写法：第二版负责整体组织，原有规范负责完整性和质量控制。

本规范基于历史 PRD 样例的写作方式提炼，仅吸收文档结构和表达方法，不继承历史项目中的业务名称、角色、流程、字段或规则。

配套文件：

- `00_项目口径库/PRD结构模板.md`
- `00_项目口径库/PRD质量检查清单.md`
- `00_项目口径库/PRD常用表达库.md`

## 2. 核心写作原则

### 2.1 事实分级

正文中的业务判断必须使用以下标签：

| 标签 | 使用条件 | 写作要求 |
| --- | --- | --- |
| 【事实】 | 已由高优先级资料明确记载，或已在当前有效系统中验证 | 写明来源，不扩展未确认规则 |
| 【推断】 | 根据现有页面、流程或数据关系得出的合理判断 | 说明推断依据，不写成确定规则 |
| 【建议】 | 产品、交互或技术层面的优化方案 | 说明目的和影响范围 |
| 【待确认】 | 缺少业务口径、数据来源、权限或边界条件 | 转入“待确认问题”统一编号 |
| 【历史资料】 | 仅来自旧系统、历史 PRD 或历史截图 | 不得直接作为现行验收依据 |

#### 2.1.1 反向补档 PRD 例外

从开发页面、现有系统、页面源码或截图反向整理形成的 PRD 不使用上述五类方括号标签，正文也不解释事实分级或标签体系。反补文档通过章节和表格结构区分内容性质：页面实际表现写入“页面现状”，目标方案或原型补充写入“设计补充”，现状与目标不一致写入“差异说明”，来源性质写入“来源与依据”，未决事项集中写入“待确认问题”。

对外交付的 PRD 只呈现业务目标、范围、功能、页面、字段、交互、状态、权限、异常、接口和验收要求，不描述反向整理、页面采集、文档生成或原型制作过程。正文及文档信息不得出现 Agent、AI、工具名称、内部规则文件、内部目录路径、环境网址、账号或密码；来源说明不得写系统访问网址。上述内部信息仅保留在任务记录、采集台账或差异记录中。

未决事项使用“待确认-xxx”稳定编号；正文需要关联时直接写“见待确认-xxx”。反补文档仍须记录依据、保持可追溯且不得编造规则。反补内容经确认并转为正式 PRD 后，重新执行 2.1 节的通用标签规则。

### 2.2 来源优先级

1. 已确认修改意见和项目固定口径；
2. 经业务方确认的会议纪要；
3. 正式政策文件、需求文件和接口材料；
4. 当前有效 PRD 与原型；
5. 历史系统、历史 PRD 和页面截图；
6. 产品推断与设计建议。

低优先级资料不得覆盖高优先级口径。存在冲突时，应保留冲突说明并登记待确认问题，不得自行选择一种写成事实；正式 PRD 可使用【待确认】标签，反向补档 PRD 按 2.1.1 节集中登记且不使用标签。

### 2.3 可执行与可验收

- 每条需求应能映射到页面、字段、操作、状态、权限或接口。
- 每个操作应说明前置条件、执行动作、结果反馈和失败处理。
- 每条验收标准应可观察、可重复验证，并具有明确通过条件。
- 避免使用“支持相关功能”“按需处理”“操作友好”等不可验证表达。

## 3. 文档整体结构

某政务项目 PRD 统一采用以下结构。无内容的可选章节可以标记“不适用”，不可直接删除导致结构失真。

| 顺序 | 章节 | 必选 | 说明 |
| --- | --- | --- | --- |
| 0 | 文档信息 | 是 | 文档名称、版本、状态、责任人及更新时间 |
| 1 | 文档说明 | 是 | 编写目的、需求来源、术语和关联材料 |
| 2 | 修订记录 | 是 | 版本、日期、修改范围、来源及确认人 |
| 3 | 业务背景与产品定义 | 是 | 现状、目标、产品类型、核心对象、能力边界、能力架构和功能清单 |
| 4 | 适用范围 | 是 | 端口、角色、功能、页面、流程和数据范围 |
| 5 | 不做范围 | 是 | 本期不实现、暂缓或由其他模块承接的内容 |
| 6 | 用户角色 | 是 | 标准角色、职责、参与环节和数据范围 |
| 7 | 页面清单 | 是 | 页面、弹窗、抽屉、入口、退出路径及页面结构 |
| 8 | 业务流程 | 按需 | 触发、主流程、分支、异常、终止条件和状态变化 |
| 9 | 核心功能说明 | 是 | 按功能清单逐项展开需求来源、输入、处理、输出、权限、异常和验收 |
| 10 | 字段说明 | 是 | 查询字段、表单字段、列表列和按钮操作 |
| 11 | 状态流转 | 是 | 业务状态、合法流转和页面状态 |
| 12 | 权限控制 | 是 | 页面、按钮、数据范围和字段权限 |
| 13 | 校验规则 | 是 | 必填、格式、范围、唯一性、跨字段和状态校验 |
| 14 | 异常场景 | 是 | 空、错、无权限、重复、并发、超时及恢复方式 |
| 15 | 接口、数据与非功能要求 | 按需 | 接口、数据、字典、附件、安全、性能、兼容性和可维护性 |
| 16 | 日志 / 留痕 | 按需 | 关键操作、变更前后值、保存期限和查询权限 |
| 17 | 消息通知 | 按需 | 事件、对象、渠道、模板、失败重试和跳转 |
| 18 | 验收标准 | 是 | 按前置条件、操作和预期结果给出可验证的通过条件 |
| 19 | 待确认问题 | 是 | 问题、依据、影响、优先级和建议确认方 |
| 20 | 发布前检查 | 是 | 核对结构、口径、编号、原型和相关项目资产 |

推荐“一份 PRD 对应一个业务模块或一组强相关页面”。当文档超过三级功能目录、跨越多个独立角色闭环或难以单独验收时，应拆分 PRD，并通过总则或流程文档建立关联。

## 4. 章节命名与编号

### 4.1 命名原则

- 章节名称使用名词短语，如“角色与权限”“状态流转”“异常场景”。
- 功能章节使用“对象 + 动作”或页面名称，如“申请记录查询”“详情查看”。
- 避免“其他”“相关功能”或仅写“功能一”等无法定位内容的名称；中文序号后必须补充“对象 + 动作”。
- 角色差异不是页面名称的一部分时，不使用大量方括号前缀堆叠标题。
- 同一概念只使用术语表规定的标准名称。

### 4.2 编号规则

- 一级标题：`1. 文档说明`
- 二级标题：`1.1 编写目的`
- 三级标题：`1.1.1 需求来源`
- 正文步骤：`1.`、`2.`、`3.`
- 面向业务阅读的标题使用中文序号，例如“功能一：查询与重置评委会”。
- 跨章节引用使用中文稳定编号，例如：规则编号 `规则-001`、验收标准 `验收-001`、待确认问题 `待确认-001`、异常场景 `异常-001`。
- 每份 PRD 独立编号，各编号类别均从 `001` 开始并连续递增；编号在同一份 PRD、同一类别内唯一。
- 跨文档或结构化台账中的引用，以“模块/PRD 名称 + 稳定编号”为联合标识，不把单独的 `功能-001`、`字段-001` 等视为全项目唯一编号。
- 统一编号前缀为：`来源-`、`页面-`、`功能-`、`输入-`、`输出-`、`规则-`、`字段-`、`列表字段-`、`操作-`、`业务状态-`、`页面状态-`、`权限-`、`校验-`、`异常-`、`接口-`、`数据-`、`字典-`、`日志-`、`消息-`、`验收-`、`待确认-`、`不做-`。
- 当前有效 PRD 不再使用英文编号前缀；历史归档文档可保留旧编号，升级为当前版本时必须转换。

正文标题原则上不超过三级。页面内部的小块内容优先使用表格标题、加粗标签或列表，不继续增加第四、第五级标题。

## 5. 功能说明颗粒度

### 5.1 推荐颗粒度

功能说明的最小单元是“用户可感知、系统可反馈、测试可验证的一次操作或规则”，应至少回答：

1. 谁可以操作；
2. 在什么条件下操作；
3. 从哪里进入；
4. 操作什么对象；
5. 系统校验什么；
6. 成功后发生什么；
7. 失败或不满足条件时如何处理；
8. 是否引起状态、权限或数据变化。

### 5.2 功能单元模板

| 项目 | 内容 |
| --- | --- |
| 功能编号 | 使用 `功能-001` 等稳定中文编号 |
| 功能名称 | 使用“对象 + 动作”命名 |
| 需求来源 | 引用真实存在的来源编号，不得伪造来源 |
| 使用角色 | 关联标准角色 |
| 入口 | 菜单、页面或上游操作 |
| 前置条件 | 状态、权限、数据完整性等 |
| 操作步骤 | 按用户动作和系统响应编号 |
| 业务规则 | 引用规则编号 |
| 成功结果 | 页面反馈、数据变化、下一状态 |
| 失败处理 | 提示、数据保留、重试方式 |
| 关联内容 | 页面、字段、接口、状态或验收标准 |

### 5.3 不推荐写法

- 只写按钮名称，不写出现条件和执行结果。
- 一个段落同时描述入口、字段、权限、流程和异常。
- 依赖截图表达全部需求，正文只写“见下图”。
- 将接口实现、数据库表结构和用户需求混写在同一功能描述中。

## 6. 页面说明颗粒度

每个独立页面、弹窗或抽屉应作为一个页面单元描述。页面单元至少包含：

### 6.1 页面定位

| 项目 | 内容 |
| --- | --- |
| 页面名称 | 与原型和菜单保持一致 |
| 页面类型 | 列表页、详情页、表单页、工作台、弹窗、抽屉等 |
| 所属端口 | 个人申报端、单位经办端、政务管理端、专家评审端等 |
| 主要用户 | 使用标准角色 |
| 进入方式 | 菜单、按钮、待办、链接或系统跳转 |
| 退出方式 | 返回、关闭、提交后跳转等 |

### 6.2 页面结构

使用表格说明页面区域，不按截图坐标逐项描述。

| 区域 | 内容 | 交互与规则 |
| --- | --- | --- |
| 标题区 | 页面名称、状态、说明 | 是否固定、是否随数据变化 |
| 筛选区 | 查询条件 | 默认值、联动、重置 |
| 主内容区 | 表单、列表、详情等 | 加载、编辑、展示规则 |
| 操作区 | 页面级和行级操作 | 权限、状态和前置校验 |
| 状态区 | 加载、空、错、无权限等 | 页面反馈和恢复方式 |

### 6.3 页面交互

- 页面跳转应写明来源页面、目标页面和携带参数。
- 弹窗用于新增、编辑、确认等短流程；抽屉用于需要保留当前上下文的辅助查看或配置。
- 长表单和独立业务任务应使用二级页面，不为减少页面数量而堆叠。
- 截图和原型用于辅助定位，正文必须保留可检索的文字规则。

## 7. 字段表写法

历史样例中存在“字段散写在正文”“字段名与规则写在同一句”和“仅用截图表达字段”的情况。某政务项目统一使用结构化字段表。

### 7.1 表单字段表

| 列名 | 必选 | 写作要求 |
| --- | --- | --- |
| 字段名称 | 是 | 与页面文案一致 |
| 控件类型 | 是 | 输入框、下拉框、日期、单选、上传等 |
| 是否必填 | 是 | 写“是/否/条件必填”，条件必填需说明条件 |
| 默认值/回显 | 是 | 无默认值写“无” |
| 数据来源 | 是 | 用户录入、系统带入、字典、接口、上游数据等 |
| 可见/可编辑条件 | 是 | 说明角色、状态和联动条件 |
| 校验规则 | 是 | 格式、长度、范围、唯一性、跨字段校验 |
| 联动规则 | 按需 | 触发字段、目标字段和变化结果 |
| 敏感级别/脱敏 | 按需 | 敏感字段的展示和权限要求 |
| 错误提示 | 是 | 给出明确、可执行的提示语 |

字段技术标识、数据类型和长度只有在已确认且有助于研发联调时才写入 PRD；完整技术字段定义沉淀到字段字典，不在多个 PRD 中重复维护。

### 7.2 列表字段表

| 列名 | 数据来源 | 展示格式 | 排序/筛选 | 权限与脱敏 | 空值处理 |
| --- | --- | --- | --- | --- | --- |
|  |  |  |  |  |  |

### 7.3 按钮操作表

| 操作 | 出现条件 | 可用条件 | 前置校验 | 成功结果 | 失败处理 |
| --- | --- | --- | --- | --- | --- |
|  |  |  |  |  |  |

不要将多个字段压缩在同一个单元格或长句中。一个字段一行，一个规则可追踪到一个字段或规则编号。

## 8. 流程说明写法

### 8.1 流程结构

每条业务流程按以下顺序编写：

1. 流程名称与目标；
2. 参与角色；
3. 触发条件；
4. 前置条件；
5. 主流程；
6. 分支流程；
7. 异常流程；
8. 终止条件；
9. 后置结果；
10. 状态变化；
11. 关联页面、接口和通知。

### 8.2 主流程表

| 步骤 | 操作角色 | 用户动作 | 系统响应 | 状态变化 | 关联页面 |
| --- | --- | --- | --- | --- | --- |
| 1 |  |  |  |  |  |

流程步骤使用动宾结构。用户动作和系统响应分开描述，不使用一个超长段落连续书写。

### 8.3 分支与异常

- 分支使用 `分支-01`、`分支-02` 编号，并注明从主流程哪一步进入、何时回归。
- 异常使用 `异常-01`、`异常-02` 编号，并说明是否可重试、是否保留数据。
- 跨角色流转必须写明上一角色的输出和下一角色的待办来源。
- Mermaid 流程图是辅助表达，不能代替步骤表和状态表。

## 9. 权限说明写法

历史样例常将权限写在页面入口或提示语中，难以检查菜单、按钮和数据范围是否一致。某政务项目必须同时描述以下四层权限：

1. 菜单/页面权限；
2. 按钮/操作权限；
3. 数据范围权限；
4. 字段可见与可编辑权限。

### 9.1 权限矩阵

| 角色 | 页面/功能 | 可见范围 | 可执行操作 | 字段权限 | 无权限表现 |
| --- | --- | --- | --- | --- | --- |
|  |  |  |  |  |  |

权限描述应采用“角色 + 对象 + 范围 + 动作”的句式。无权限时应明确是隐藏入口、置灰、只读还是提示无权限；前端隐藏不能替代服务端鉴权。

权限变化应同步更新 `00_项目口径库/角色权限口径.md` 和 `02_结构化台账/权限矩阵.csv`。

## 10. 状态说明写法

### 10.1 业务状态

业务状态必须集中定义，不在多个页面章节中各自创造状态名称。

| 状态编码 | 状态名称 | 进入条件 | 可执行操作 | 退出条件 | 下一状态 | 是否终态 |
| --- | --- | --- | --- | --- | --- | --- |
|  |  |  |  |  |  |  |

状态变化需与操作、角色和流程步骤关联。禁止使用“处理中”“已完成”等名称相同但含义不同的状态。

### 10.2 页面状态

按适用范围覆盖：

- 初始状态；
- 加载中；
- 有数据；
- 无数据；
- 查询无结果；
- 只读；
- 编辑中；
- 校验失败；
- 保存中、提交中；
- 保存成功、提交成功；
- 接口异常；
- 权限不足；
- 数据不存在；
- 已过期或不可办理。

页面状态应说明页面表现、按钮状态、提示语和恢复方式，不能只在流程章节写状态名称。

## 11. 异常场景写法

异常场景单独编号，不混在主流程步骤或备注中。

| 异常编号 | 触发条件 | 系统处理 | 用户提示 | 数据处理 | 恢复方式 | 日志/通知 |
| --- | --- | --- | --- | --- | --- | --- |
| 异常-001 |  |  |  |  |  |  |

至少检查以下异常类型：

- 必填、格式、范围和跨字段校验失败；
- 数据不存在、已删除或已被其他用户修改；
- 重复点击、重复提交和幂等；
- 接口失败、超时和部分成功；
- 权限不足或数据越权；
- 附件上传、下载或预览失败；
- 状态已变化导致操作失效；
- 字典、组织或关联数据缺失；
- 申报期结束、事项停用或记录过期。

提示语应说明“发生了什么”和“用户下一步可以做什么”，避免只写“操作失败”。

## 12. 验收标准写法

历史样例普遍缺少独立、可测试的验收标准。某政务项目每个关键功能必须关联验收标准。

### 12.1 推荐格式

| 编号 | 前置条件 | 操作 | 预期结果 | 关联需求 |
| --- | --- | --- | --- | --- |
| 验收-001 |  |  |  |  |

### 12.2 编写要求

- 一个验收标准只验证一个主要结果。
- 写明角色、数据状态、输入条件和权限范围。
- 预期结果应包含页面反馈、数据变化和状态变化。
- 正常、边界、异常和无权限场景分别覆盖。
- 数量、时间、格式、排序、脱敏等要求使用明确值或可引用配置。
- 不使用“功能正常”“展示正确”“体验良好”等主观表达。

验收标准应能直接转化为 `07_测试验收` 下的测试点。

版本记录只在文档前部集中维护，不在每个功能或用例下重复维护。

### 13.3 版本号规则

- `V0.x`：草稿或评审中版本；
- `V1.0`：首个确认基线；
- `V1.x`：兼容性增补、规则澄清或局部修改；
- `V2.0`：范围、流程或核心模型发生重大变化。

每次变更应写明影响的章节、页面、字段、流程或状态，不使用“优化部分内容”“调整需求”等模糊描述。

## 14. 历史写法差异与推荐方式

| 观察到的不一致写法 | 风险 | 某政务项目推荐 |
| --- | --- | --- |
| 有的按系统概述和功能模块叙述，有的按角色页面逐步叙述，有的按完整用例模板叙述 | 文档之间难以横向查找 | 统一采用“模块总览 + 页面单元 + 流程/状态 + 验收标准”结构 |
| 标题层级从二级到五级不等，部分标题仅靠加粗和字号表达 | 目录失真、无法稳定引用 | 最多三级标题，使用 Markdown 标题和稳定编号 |
| 功能说明有的只有目标性描述，有的逐按钮、逐提示语展开 | 颗粒度不一致 | 以一次可操作、可反馈、可验收的功能单元为最小颗粒度 |
| 页面需求大量依赖截图或把全部内容写在“页面逻辑”长段落中 | 不可检索、规则易遗漏 | 截图辅助定位；页面结构、字段、操作、状态和异常分别结构化描述 |
| 字段散写在正文、合并在一句话或仅出现在截图中 | 难以研发和测试对照 | 表单字段、列表字段、按钮操作分别使用标准表格 |
| 流程有的只放流程图，有的只写操作步骤 | 角色交接和状态变化不清 | 流程图 + 主流程表 + 分支/异常 + 状态表组合使用 |
| 权限有的写在入口说明，有的只给无权限提示 | 无法检查数据权限和字段权限 | 使用四层权限模型和统一权限矩阵 |
| 状态散落在列表说明、按钮规则和提示语中 | 状态枚举不一致 | 集中维护业务状态表，页面章节补充页面状态表现 |
| 异常通常附在正常流程末尾或没有编号 | 难以覆盖和追踪 | 独立异常表，说明触发、提示、数据保留、恢复和日志 |
| 多数文档缺少独立验收标准 | 无法形成明确交付边界 | 所有关键功能使用“前置条件—操作—预期结果”编写验收编号 |
| 有的只有文档级变更记录，有的每个用例都重复修订日志 | 维护成本高、信息冗余 | 仅维护文档级版本记录，变更内容引用需求编号 |
| 有的保留大量空模板章节 | 文档冗长且误导读者 | 必选章节必须填写；可选章节标记“不适用”并说明原因 |

## 15. 语言与格式要求

- 使用简体中文、主动语态和明确主语。
- 操作使用“点击、选择、输入、上传、提交”等动词。
- 系统反馈使用“系统展示、系统校验、系统保存、系统流转”等表达。
- 同一文档中的页面、按钮、字段和状态名称必须与原型一致。
- 引用按钮或字段时使用中文引号，如“提交”“审核状态”。
- 规则使用编号，不用颜色、批注或截图标色作为唯一表达。
- 表格只承载重复结构化信息；长篇背景和原因使用短段落。
- 原型示例值必须注明为示例，不得作为真实字典或业务规则。
- 功能标题采用“功能一：对象 + 动作”，页面标题采用“页面一：页面名称”；跨章节引用使用中文稳定编号。
- 平台通用能力型 PRD 应先给出产品定义、能力架构和功能清单，再展开核心功能明细。

## 16. PRD 完成定义

一份 PRD 只有在满足以下条件后，方可进入评审或开发：

1. 来源、范围、角色和业务目标明确；
2. 页面、字段、按钮、权限、状态和异常描述完整；
3. 主流程、分支流程和跨角色交接可闭环；
4. 所有未确认内容已编号并进入待确认问题；
5. 关键功能均有可测试的验收标准；
6. 与原型、字段字典、按钮操作表、权限矩阵、状态流转表一致；
7. 包含不做范围和版本记录；
8. 通过 `PRD质量检查清单.md` 检查。
